# Proposed integration plan: what the walking skeleton suggests for the real server

*2026-11-03, spike-walking-skeleton. These are suggestions with reasons, for whoever builds the council server (Joseph's "server and channels/mcp adapters for a working council system"). Each cites the run record that motivates it. Where a suggestion is my inference rather than something a run showed, it says so. The council *logic* (contention, charter, agenda) is the sibling spikes' ground; I touch it only where a mechanic forced it. Revised after two independent passes (`de-novo-feedback-1.md`, `de-novo-feedback-2.md`); `response-to-de-novo-1.md` and `response-to-de-novo-2.md` say what changed.*

## 1. Keep: the shape that survived contact

1. **Pure core + any-process store, no daemon.** State = fold(charter, canonical log); one function turns a closed round's intents into derived events; any process holding the council directory can close a round whose condition holds, under an flock. Every model-member meeting, across four harnesses, closed every round exactly once. Every log is internally consistent: chain, derived events and sealed files all agree (`steward replay`). The verifier added 20 concurrent writer processes on one directory, which held (`verify-1` test C). vsect's choice (shared state under a common directory, no server) works here too. *Inference:* a daemon becomes worth it only when members are remote, or when the council directory must be out of members' reach (§3.4).
2. **Sealed intents outside the log; only the close enters it, sorted by seat.** That keeps arrival order out of the canonical log by construction. `steward selftest` (50 shuffled orders → 1 log) guards the resolver against a change that would read order; it does not test the wall-clock facts (`gone`, `absent`, `closed_by`), which are recorded as facts by design. Wall-clock receipts go in a separate, non-canonical journal. **Tell the member what the charter says:** the first build promised replacement in the tool description and the view while the store refused it (verifier's D5).
3. **Submissions are final within a round.** With replacement allowed, the same intents in shuffled orders gave 4 distinct logs: a revision races the "everyone has submitted" close. Either submissions are final (as now), or close waits for a deadline (and wall-clock order decides again). A member who wants to change course does it next round. If revision is ever wanted, the latency-invariant form is an explicit *two-phase* round (submit, then a separate "seal" act), and that costs a round-trip per round.
4. **Close = everyone submitted, or gone; the wall clock only as a long backstop.** Measured: once the last member answered, the round closed at once, so a round lasted as long as its slowest member (2–18 s after opening in `trial-4`). The last seat in was grok's in 5 rounds and agy's in 4, and nobody was penalized. A member whose process died stopped holding the round up one lease later (~20–30 s: `trial-1`, `trial-3`). Slow thinking is never absence, because liveness is the seat holder's lease, refreshed by the server process (or the driver), not by the model. **And a member that stops looping must not stall every round** (first verifier's D3). A seat that was absent, not gone, in k consecutive rounds that each ran to the backstop is stalled (`absent_rounds_to_gone`, default 2): later rounds stop waiting for it. **Any call from its holder clears the stall**, and the open round waits for it again. Two details matter, both found by the second verifier:
   - The first version counted rounds that never waited for the seat (a crashed seat, gone, in rounds that waited for someone else).
   - It cleared the stall only by a submission that landed in a close. Rounds closed the instant the others answered, so a returning member had to out-race them (`de-novo-feedback-2` §2.1–2.2).

   Judging stalls by "no call in flight for a while" would penalize a thinking member, which looks the same from the server.

   **This is a majority-council rule.** A council that decides by unanimity or holds the item must never shrink: it sets `absent_rounds_to_gone: 0`. A silent seat then holds the item, or is re-seated from its line (`reaction-line-of-stewards.md`; re-seating is not built).

   **A seat that never seats costs its first round the whole `arrival_grace_s`:** 180 s measured, when grok was out of quota and never started (`verify-2/runs/mixed-rerun2`). After that it costs nothing. That is a charter number to choose deliberately.
5. **One blocking `council_wait` that sends progress every ~10 s** is the universal member loop. It worked in Claude Code `-p`, codex, grok and agy (`harness-notes.md`).

## 2. Change: what running showed was wrong in the first design

1. **A returned result is not a delivered result.** Claude Code's idle-timeout abort and codex's 60 s timeout send the server no cancellation (`probes/p4`, `probes/c2`). So nothing in the server may treat "my wait call returned" as "the member saw it". Rounds wait on *submissions*. Any "member was informed" fact the record needs (e.g. for the charter-agenda spike's common-state condition) must come from the member's own act naming the round it answers, which `council_submit(round=…)` already requires. **That is only as strong as the delivery state behind it.** The second verifier showed an abandoned `council_wait` advancing the seat's cursor, so the member's live wait could render with no reveal in it (`de-novo-feedback-2` §2.3, and live in `bg-wait-2-sonnet`). Two rules now hold:
   - The seat's cursor advances **only when its submission is accepted** (its own act), so every view the member can act on carries everything since its last act.
   - A newer `council_wait` on a seat **supersedes** an older one, which returns without rendering.

   With both, naming round rN again proves the view acted on carried the reveal of rN−1.
2. **Seat identity: one live holder per seat, keyed to a principal, with an epoch.** In `trial-3` a fresh session holding an already-held seat lost every round only because it was slower: the other holder's submission completed the round, and the newcomer's arrived to "round is not open". It never learned another process held its seat, and had it been faster, a mind with no memory of rounds 1–7 would have voted. Now (tested by RPC, `tests/regression.py`; by model, `trial-3b`, `trial-4c`, `trial-5c`) a seat has one holder. A holder is a principal: a launcher-declared id such as a driver, else codex's `sessionId` or agy's `root_conversation_id` from `_meta`, else the harness process. The principal is only what the caller *asserts*, so a holder is that principal **plus a holder key**, a secret held by the connection or its launcher that the client never sends. Without the key, two connections presenting one codex `sessionId` were one holder (`de-novo-feedback-2` §2.5). A second principal is refused, and told why, while the holder's lease is live. A clean exit releases at once; a crash lapses after the lease. The epoch increments, and the minutes show who held each seat when. **The holder must be whatever outlives the turns.** In driver mode each turn's server process released the seat on exit, leaving it open to anyone with the token between turns (verifier's test A). Now the driver claims and refreshes its seats, and servers under a launcher-declared principal don't release. **And the holder's lease is the one measure of liveness:** a separate presence heartbeat disagreed with it both ways (verifier's §4.5; my backstop test).
3. **Every piece of per-member state belongs to the seat holder, persisted, never to the process.** The delivery cursor lived in process memory, so in driver mode every turn re-sent the whole log (rec's transcript: ~573k characters of user-side content, of which the driver's prompts were ~75k; the rest was tool results re-sending the log). The cursor fix cut driver cost per round by ~62% ($0.0166 in `trial-5` → $0.0063 in `trial-5b`). Measuring cost needs care: in a resumed `claude -p` session, `total_cost_usd` and `modelUsage` are cumulative over the session (each turn's equals the running sum of the per-turn `usage`), so a meeting's cost is each seat's last turn, never the sum of its turns. The cursor is now keyed to (seat, principal) on disk. A new holder starts from nothing and gets a full catch-up, which is right for a returning member.
4. **Never advertise an optional identity field to a model.** Haiku filled `seat_token` with its seat name and locked itself out (`trial-1`). Single-seat servers no longer show the field; multi-seat (shared-connection) servers require it. Even required, two subagents dropped it once on a long submit (`trial-2`); the server refused, and they retried. Errors must say exactly what happened (*"this connection already holds seat X: call again without seat_token"*).
5. **Liveness counts only the holder.** A refused duplicate must not make a dead holder look alive (found while fixing 2). Since the verifier's pass, liveness is read from the holder's lease alone.
6. **Never log or pass a credential where a transcript keeps it.** The server logged its own argv, `--token` included (fixed). Multi-seat mode passes the token as a tool argument, so it lands in every harness transcript (verifier's §4.7). For subagents, the docs say an inline `mcpServers` entry gives each subagent its own connection, which could carry its token in env instead. *Untested here.*
7. **Record late intents; never drop them silently.** A submission that arrives after its round closed is refused, and its content is now kept in the receipts. This agrees with `contention.md` F4.

## 3. Add: what the real server needs that the skeleton lacks

1. **Two member adapters, one round protocol** (both run here):
   - *client*: the member loops on `council_wait` (`trial-1`…`trial-4`). Right for headless `-p`/`exec` members whose whole job is the meeting. Cheapest: one session, one growing context (about $0.0012 per member per round with haiku: `trial-3b` rec, $0.0164 over 13 rounds).
   - *driver*: the council resumes each member's own session for a turn whenever a round is open for it (`claude -p --resume`; `trial-5`, `trial-5b`, `trial-5c`). A turn may cover several rounds, because the submit reply shows the next round's view. Costs ~1.8× a client per round (haiku, `trial-5b` vs `trial-3b`, each seat's last turn). Right for members that must not sit blocked: prepared experts (first turn `--resume EXPERT --fork-session`, honoring "always fork, never resume an expert"), interactive or `--bg` sessions, and harnesses whose tool timeouts are short. The driver holds the seats it drives (claims, refreshes, releases) and passes one principal and holder key to all its per-turn server processes. **At most one turn per seat per round.** A turn that ends without a submission (an API error, a model that says it will wait) is recorded and not repeated. Before this, the driver relaunched such a turn about once a second with no cap (`de-novo-feedback-2` §2.4). Other harnesses have the same hook: codex `exec resume`, agy `--conversation`. *Inference, untested here.*
   - *backgrounded wait* (Claude Code main/background conversations only): a `council_wait` still running at 120 s becomes a background task, with or without progress (`probes/b1`; `verify-2/runs/bg-wait-2-sonnet`). It wakes the member **only if the member ends its turn** after the backgrounding. `b1`'s prompt said so; `members/brief.md` said "call council_wait again", and the verifier's member did, leaving two waits pending. `members/brief-bg.md` now says to end the turn. A `--bg` session also gets more than a `-p` session from the same flags: the interactive system prompt, and on this machine 22 Chrome browser tools (`harness-notes.md`). The launch needs `--no-chrome`. **Re-run with both changes (`runs/trial-6-bg-attempt1`, `-attempt2`): blocked by a harness startup race.** In both runs the session's first API request carried **0 tools**, about 200 ms after the council server had answered `tools/list`. The model either produced nothing or wrote its call as plain text, then ended its turn, and nothing woke it. That makes 3 of 4 `--bg` launches so far; the one exception had Chrome enabled. `--no-chrome` did remove the Chrome section from the prompt. The brief change is untested, since no member reached the council. **Until the race is understood or avoided, this adapter can't be relied on.**
   - channels / MCP tasks (Claude Code only) were not tested; the backgrounded wait already covers the waking need they were meant for.
2. **Per-harness launch recipes as data, not prose.** Each harness needed one non-obvious per-run setting, none of them global:
   - codex: `default_tools_approval_mode="approve"` and `tool_timeout_sec`;
   - agy: the `--settings` allow rule plus the deny hook;
   - grok: an isolated `HOME` and `--allow`;
   - Claude: `--strict-mcp-config --setting-sources ""`.

   `members/*-member.sh` are working recipes. The real server's "seat a member" command should own them, so Joseph adds a non-Anthropic member by naming harness + model, not by editing scripts.
3. **Record what the harness asserts about the caller, as an assertion.** codex and agy put session/conversation ids in `_meta`; record them on every act (the skeleton does, in receipts). They are claims the client makes, and any client can make them. Seat exclusivity therefore also rests on a holder key (§2.2), and a remote or multi-user server needs a real per-holder secret. For Claude Code, `CC_AGENT` never reaches an MCP server (it is a Bash-prefix hook). The launcher can pass the session it started as the principal. *Suggestion:* the agent-identity hook could also export into MCP server env, but MCP servers start before the first Bash call, so it would have to be a different mechanism. Out of scope here.
4. **Sealing, and the record itself, must be enforced by where the council directory lives, not by etiquette.** Sealed intents sit in the council directory, readable by any member with file tools, and the log is just as writable. The verifier flipped every vote in a round and regenerated a log that passed replay. The skeleton now has a partial answer: each member's server records the chain heads it showed its member in its own log, outside the council directory, and `steward witness` checks the log against them. That catches a rewrite unless every member's log is rewritten too. The agy member reached for `run_command`/`read_file` unprompted (to read its own tool schema, `trial-4/fam/agy-hook.jsonl`; the hook denied both). Today sealing holds only because every launcher withholds file access (`--tools ""`, codex `--disable shell_tool`, grok `--tools search_tool,use_tool`, agy deny hook). For members that keep their file tools (prepared experts do), the council directory must live where they can't read or write it: a daemon's memory, a directory outside their sandbox, or encrypted to the closer. That is the first concrete reason for a daemon.
5. **codex leaks the enclosing git repository's path, remote and HEAD to every MCP server** (`x-codex-turn-metadata.workspaces`; it walks up from the member's cwd to the repo root). Fine locally; know it before any council server is remote.

## 4. For the council-logic spikes (observed, not designed here)

The meetings examined for them (named per item) all hit these. They are offered as data:

1. **Members need `amend`.** Without it they routed around the gap in a different way almost every meeting:
   - voting yes on text they had all superseded, with dissent notes attached to each vote (`trial-2`);
   - the maker withdrawing so the substitute could be moved (`trial-4`);
   - unanimously *rejecting* their own pending motion (0–3) so they could move the agreed text (`trial-5`);
   - a 1–2 rejection, a restatement, a withdrawal and a re-move (`trial-5b`);
   - a second motion on the same item to "reaffirm and clarify" (the verifier's re-run).

   In each, the adopted text and the members' actual consensus diverged until the workaround landed.
2. **Near-duplicate motions are the common case, not the edge.** In `trial-4` all four seats moved the agreed substitute in one round. Two texts were byte-identical (co-made); two differed in wording and were recorded as rival standing intents, which then lapsed. The record says two members moved it and two were overruled; in fact all four moved the same thing. `initial-thoughts.md` §1 predicted this; it occurs at the first opportunity.
3. **The view must explain resolution.** Members asked how the winning motion was chosen ("The view did not say how that one was chosen", grok seat). The ladder is in the event (`ladder:`) but not in what the member reads.
4. **Standing intents need a "superseded by" path.** Members were asked to re-affirm intents the group had moved past (claude seat, trial-4).
5. **Debate ended by the round limit, not exhaustion, when one member kept making procedural notes** (`trial-2`). A full round of passes ended debate in every other case. The first build reset that limit when one co-maker withdrew (verifier's D1); a partial withdrawal is now its own event and leaves the count alone.
6. **"Inquorate for N rounds" has no duration** (verifier's D2): an all-gone council adjourns two ticks after the leases lapse. How long a council waits for a quorum is a charter question.

## 5. How the sibling spikes meet this one

- **charter-agenda's common-state condition** (*every act applied at s_k was formed by a member who held s_k*) is enforceable as §2.1 says: by the act naming its round, never by the server believing it delivered, and only because a view is never consumed by sending it (the cursor advances on the member's act). Its result "rounds → majority valid; polling → unanimity only" [51:2] applies to driver mode unchanged: driver mode is still rounds.
- **contention-rounds:** the arrival-order invariance property holds in the store as built; whatever resolver that spike settles on can be dropped into `core.step` and checked with `steward selftest`'s shuffle harness. The replacement-race result (§1.3) is a constraint on any resolver design that allows revision. Its F4 ("a late response is logged as supplementary, never silently dropped") is now what the store does (§2.7).
- **Keep the skeleton as a test bench** (the verifier's suggestion, taken): it is what produced the amend and near-duplicate evidence. Running real members against each candidate resolver is cheap and teaches what reading cannot.

## 6. Suggested order for building the real server

*(My judgment about sequencing; not something a run showed.)*

1. Port `core` + `store` as they now stand, with `tests/regression.py` as acceptance (it runs both verifiers' tests):
   - seats held by whatever outlives the turns, keyed to principal plus holder key;
   - holder-lease liveness;
   - cursors advanced only by the member's act, and superseded waits;
   - final submissions;
   - stall escalation counting only rounds that waited for the seat, cleared by any call (majority mode only);
   - late intents recorded;
   - witness heads.
2. The client adapter and launch recipes for the four harnesses (§3.2).
3. The driver adapter, for prepared experts and other members that must not sit blocked. Each turn is a `-p` process, which showed no startup race in any run. (The first verifier advised moving the `--bg` wait ahead of the driver, and I did. `trial-6-bg` reverses that: 3 of 4 `--bg` launches went out with no tools.)
4. The backgrounded wait (§3.1), once the `--bg` startup race is understood or avoided. Launch with `--no-chrome` and `members/brief-bg.md`.
5. Decide where the council directory lives (§3.4) before seating any member with file tools.
6. Then the council logic from the sibling spikes, amend first.
