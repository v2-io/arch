# vsect

Work inside a verisectorium: a corpus of small named records where every record must carry its own honest epistemic state, because every mind that works on it arrives with no memory of earlier sessions. Bare `vsect` shows where the store stands. Every number it prints is computed from the records and the recorded acts; none can be typed.

The design is at `~/src/aat-v3/msc/vsect/` (`README.md` → `model.md` → `vsect.md` → `core.md` → `storage.md` → `open.md`). This is its first working version, built 2026-10-30 against ASF (`~/src/arch/asf/`) as the first live corpus, under objective I.3/I.4 of ASF's `msc/inside-out-2026-10/INTENT.md`. It is the design's "what comes first" (`vsect.md` §8): it infers nothing about truth.

```sh
cargo install --path firmatum/utils/vsect   # from ~/src/arch/; puts `vsect` on PATH beside aspectus and md-press
cd ~/src/arch/asf && vsect                   # the dashboard
vsect help · vsect help model · vsect help <verb>
```

## What it does

- **Dashboard** (bare `vsect`): what is known broken, what is waiting and for how long, what evidence is recorded, as raw counts, as of a commit (`+dirty` when the tree differs). Exit 0 when rendered.
- **`vsect revise [<kind:slug>]`** records the two things about an edit that the tree cannot say: when a check rests on the old text of an edited record, whether the change was a rewording or a redefinition (the reviser's claim, and who made it, which `confirm` refuses on); and the fate of a record the trail speaks about that is gone (retired, or superseded by a named successor). An edit no check rests on needs no event: git has it. A version is kept under `.vsect/objects/` only while git cannot reproduce it.
- **`vsect take <reviews/x.md>`** takes in a review record's typed items: a check becomes a securing event bound to the exact versions it read (its basis); a finding stays open on its statement. A check that broke something opens a finding too. If the text changed after the check, take says so and the check stays with the version it read. Taking a review twice adds nothing. `vsect take --check <id> --criterion … --outcome …` records one check inline, writing the review record for you.
- **`vsect confirm [<id>]`** is the second mind (`core.md` §3.6, §9.1–9.2). With nothing: every (record, version the checks read → version now) pair that keeps a check from holding, with who revised it and what a confirmation would re-bind. With a record: the diff of the two stored versions, the checks concerned, and one question — *equivalent* (full stop: one event at the root re-binds every check that read the old version and everything downstream, with nothing written downstream), *for-checks* (only as it bears on the listed checks' criteria; `--criterion` says what was compared), or *not-equivalent* (those checks are ended on this pair and redone; the pair leaves the pending list). `--checks review:x#C1,…` narrows either judgment to the named checks and leaves the rest pending, so a pair that bears on one check and not the others gets a per-check verdict. It refuses the reviser. Confirmations chain (a→b, b→c confirmed means a check that read a holds at c). The diff is word-level with context, never a prefix: a confirmer once judged blind from identical-looking 160-character prefixes. A check whose own outcome was `broken`/`narrowed` is never listed: the finding it opened is the waiting item.
- **`vsect ask` / `vsect answer`** record questions with a closer (anyone, awaiting:<work>, steward-fact, steward-purpose) and close them.
- **`vsect refute <id> --ground kind:text`** records a refutation on evidence (counterexample, broken derivation, missed prediction, broken mapping; never authority) and lists what rests on the statement.
- **`vsect open [<id>]`** is the open ledger: findings, questions, items, lapsed checks and unrecorded fates, keyed by the statement they concern, oldest first, each with who may resolve it; then, apart, the imported items not yet re-checked, by source file and line.
- **Items** (`vsect note` / `vsect close` / `vsect bring --tracker` / `vsect recheck`) are work owed, with an owner, closed by the commit that did it (`close --outcome done --by-commit <sha>`, which vsect checks is a commit). `bring <tracker.md> --tracker --unit bullets|checkboxes|sections|rows` imports a tracker's units as items under `items/imported/`, each with its source file and line, its section, and the segments it names. An imported item carries the tracker's label, not the store's: this estate's record (2026-05-29) is that re-checked "ready" rows turned out stale or overstated, and other rows recorded work that had already landed, so the ledger must not start life as a cleaner-looking copy of the trackers. An imported item is listed apart, cannot be closed with `close`, and clears only by `recheck`, which records what was checked against HEAD: `holds` makes it a real item (the file moves to `items/`, gains an owner, and `--restate` carries the frame the re-check found true beside the verbatim text); `landed`, `stale`, `superseded`, `duplicate --of item:x` and `not-an-item` close it with the reason, and the closed file gets a `closed:` frontmatter line so the directory stays honest. `close` on a held item takes `done --by-commit <sha>`, `moot`, `superseded`, or `duplicate --of`; a duplicate's survivor may not itself be a duplicate (no cycles). `note --from item:x` records the roll-up an item was split out of. Owners are checked against the store's declared owner ids (`owners_from:`, ASF's INTENT KR ids); a held item whose owner is not a KR is counted on the dashboard as work no key result covers. On ASF, 2026-10-30: 371 imported items were all re-checked by a pilot and five lanes, twelve of fourteen trackers were deleted behind their last judged item, and the lane documents are under `msc/inside-out-2026-10/items-recheck/`. `items/imported/` is a verbatim provenanced copy for md-press's purposes (`.md-pressignore`); a re-checked item is a live record like any other.
- **`vsect check [--strict]`** is the lint: structural problems always (unreadable records, id collisions, frontmatter slug disagreeing with the file name, edited or misnamed event and object files, events naming events that do not exist); as notices, counted only under `--strict`: dangling edge targets (ASF's FORMAT allows `depends:` to name a planned segment, and `bin/lint-outline` owns that check), edits not taken in, lapsed checks, open items whose target is gone, and refuted statements without a mark (mark-writing is not built, so nothing could clear that yet). Exit 1 when there is anything to act on. ASF's pre-commit hook runs the plain form.
- **`vsect read <id>`** shows a record with marks above it (`✓` a check that holds · `↻` one that lapsed · `⚠` refuted, broken or an open finding · `?` an open question); `--at <version>` shows any version vsect has seen, including ones never committed; `--bare` the text alone. **`vsect why <id>`** is its history; **`vsect impact <id>`** what rests on it.
- **`vsect annotate <event-id-prefix | review:x#C1> --why "…"`** corrects the record of an act without editing it: a `correct` event naming the original (core §5.1 `corrects:`), shown by `why` beside it. Five re-check lanes used it for about thirty corrections to their own `--why` texts on 2026-10-30.
- **Read sets.** A check may declare the records in its basis it actually read (`- read: seg:a, seg:b` on a review item; `take --check … --read`), the design's `actor.read`. A change outside the read set gives the lighter verdict "upstream changed, not read by this check", counted apart; the strict rule is the default when nothing is declared. Measured need: a confirmer found 3 of about 120 (pair, check) bindings touched by their change.
- **`vsect check` notices** beyond the structural set: edits a check rests on that `revise` has not classified; lapsed checks; dangling and planned edge targets; a premise named inside an equation tag that no declared edge carries (the lapse rule cannot see it); an item closed as duplicate of an item that is itself closed non-duplicate; event files in the working tree not yet in git, by actor; stray files where records live; refuted statements without a mark.
- **Intent: `vsect claim <kind:slug>… --intent "…" [--kind edit|record] [--ttl 6h] [--alongside]`, `vsect release`, `vsect intents`, `vsect claimed <paths>`.** Joseph, 2026-10-30: *"Do you have a place/way for the agents to signal what they find and their intent? (so multiple agents finding the same evidence would see the others' notes and one or the other could signal a lock on executing the change…)"* The ledger covers what is found; a claim covers what an agent is about to do. It is a signal, not a record — not committed, not hashed — and it lives under git's *common* directory (`git rev-parse --git-common-dir`), which every worktree of the repository shares, so an integrator in its own worktree and a drain agent in the main tree see the same claims the moment they are written, with no commit and no rebase (verified across a live worktree). Claiming a record another agent holds (by harness agent key when both have one, else by `--by` name) is refused with their note shown; `--alongside` records a visible co-intent instead (two minds recording findings on one segment is fine; two editing it is the collision the claim exists to surface). Claims expire (default 6h); the holder releases, anyone releases an expired one, `--force --why` releases a live one and prints the reason. The dashboard shows live claims under "At work now"; `open <id>` and `read <id>` show claims on that record; `vsect claimed <paths>` is for the pre-commit hook (exit 1 when a touched record is claimed by someone other than `--by`; the hook warns, since a claim may be stale). **`vsect raise item:x --source "…"`** records that an existing item or finding was found again from another source, as a `raise` event, instead of a second item; `note` warns when an open item's words look close to the one being opened.
- **Durability of versions.** A check binds to content hashes; the commit is advice (`at-commit` on the event, when the review gave one). "Git can reproduce it" means *reachable from the durable ref* (`durable_ref:` in `kinds.yaml`, else `origin/main`, `main`, `master`, `HEAD`): a version held only in the working tree or only on a worktree branch is kept under `.vsect/objects/`, and `gc` drops it once the durable ref carries it. `take … at: <rev>` warns when the revision is not on the durable ref. `vsect anchors [--keep]` says where every cited version lives — kept, on the durable ref, on another ref only, or lost — and `--keep` seals the "another ref only" ones before a rebase or `git gc` can take their only commit. On asf, 2026-10-31: 283 pairs, 278 on `origin/main`, 5 kept, 0 at risk; three lanes' review records had cited worktree commits that later rebases left behind, and the bound text had landed on main under the same hash every time.
- Every writing verb ends by listing the paths it wrote ("Wrote N path(s); commit them by path: …"), so in a tree shared by several agents each commits exactly its own work with `git add <paths> && git commit -m "…" -- <paths>`.
- **Who acted is read from the harness, not typed** (2026-11-02, KR I.4). A Claude Code agent's Bash commands carry `CC_AGENT`, set by the estate's agent-identity hook (`~/src/agent-core/claude-code/agent-identity/`, a private repo on Joseph's machine) from Claude Code's own ids: `<session>/<agent-id> parent=… type=… depth=… src=agent-identity-hook/2`. When it is present, every event's actor records `agent:` (that key), `agent-type:`, `parent:` and `session:`, and `--by` becomes an optional label (default `general-purpose a4d8232a`, `main 0903e35e`). Each event also says what the record of who acted rests on: `identity: harness-agent` (the hook's key), `harness-session` (only `CLAUDE_CODE_SESSION_ID`, which a lead and all its subagents share), or `declared` (only what was typed; `--by` is then required, as before). vsect always computes `identity` and never reads it from a file. `vsect whoami` prints what would be recorded here, as a review's `author:` block. Comparisons of *who* use the agent key when both acts carry one, and names otherwise:
  - `confirm` refuses the reviser, and `review --by-revision` refuses the reviser of the answering revision, so one agent typing two names is refused and two agents typing one name are not;
  - claims are held under the key.
  - For a hand-written review taken with `take reviews/x.md`, the `author:` block is what its writer typed. It counts as `harness-agent` only when it names an `agent:` and the mind running `take` has that same key. Otherwise it is `declared`, and the taker is recorded beside it on each event as `taken-by:`.
  - Unknown actor fields are carried through unchanged, so events written by a newer vsect hash correctly in an older one. The build before this one lacked that, and reads events carrying `agent:` as edited, so reinstall (`cargo install`) rather than run an old binary on a store written by this one.
  - This is the groundwork for `item:separate-self-recorded-from-independent-evidence` in asf: that item computes, per securing event, whether its actor is among the revisers of what it checked.
  - Codex, Gemini and other harnesses have no equivalent yet; their acts are `declared`.
- Every writing verb takes `--by --role [--session]` (or `VSECT_BY` / `VSECT_ROLE` / `VSECT_SESSION`) and `--dry-run`. Questions can be answered in advance with `--answer key=value`; without a terminal an unanswered question stops the verb with exit 3. Exit codes describe the command, not the store: 0 done · 1 done, with items to act on · 2 failed · 3 not run. `--format json` on the dashboard, `check` and `open`.

## What is recorded, and what is not

An event is written only when it says something the tree does not: a check, a finding, a confirmation, a refutation, a close, an answer, a re-check, a disposal, the fate of a deleted record (retire / supersede), and a `revise` classification (reworded or redefined, by whom — what `confirm` refuses on) when a check rests on the old text. A record's existence, its text, its frontmatter and who committed it are git's to say, so there is no mint, and `ask`, `note` and `bring --tracker` write only the file. A statement version is kept under `.vsect/objects/` only while git cannot reproduce it (an uncommitted edit a check was recorded against); `read --at`, `confirm`'s diff and rename detection otherwise read the record's file at the commit whose normalized text hashes to the version. `vsect gc` drops objects git can now reproduce; `vsect migrate --prune-creation-events` is the one-time move from the first build's shape (it dropped 1,030 of asf's 1,116 events and all 1,044 objects on 2026-10-31, with every verdict identical before and after). The reason, from Joseph: every copy of something that already exists becomes *"yet another thing to integrate"*.

## What a store looks like

```text
<store>/
  .vsect/kinds.yaml                     name, steward, decider, kinds (grain, find globs, edge fields), edges, lines
  .vsect/events/<kind>/<slug>/<id>.yaml one file per act, content-addressed, never edited (`check` reports any that were)
  .vsect/objects/<2 hex>/<version>      the canonical text of every statement version seen
  reviews/<slug>.md                     what a verifier, auditor or integrator sent back, with typed items
  questions/<slug>.md                   open questions
```

Everything under `.vsect/` is committed with the store. A review record's items are sections `## C1 (check)` / `## F1 (finding)` whose fields are list items (`- target: …`, `- act: …`, `- line: …`, `- criterion: …`, `- committed: before|after`, `- outcome: …`, `- recheck: …`, and `- at: <git rev>` or `- version: …` for the text it read), then free text. Fields are list items rather than bare `key: value` lines because md-press reads a bare block as a paragraph to rewrap.

## What this version chose, where it departs from the design, and what it found

- **Grain.** ASF segments are declared as single-statement records (`segment:<slug>`), the design's `grain: record`. They are not carved into statements: of ASF's 642 equation tags, 251 carry a kebab-case id, 310 a note or condition, 81 nothing, and 38 segments carry none. Carving is the design's five-segment test (`open.md` Q10); objective B.1 will be the first to need claim-level anchors.
- **`depends:` is a meaning edge**, in the basis, transitive, `broken` on refutation. So a check on a segment lapses when anything upstream of it changes, with the cause named (`stale: own text changed` vs `stale: upstream changed (which)`). This is the design's strict rule (`core.md` §3.4–3.7) and `open.md` Q4's cost. First measurement on ASF: the F72 checks on `#deriv-evidence-allocation-ceiling` rest on a basis of 36 statement versions. One edit anywhere in that set lapses them until a different mind confirms the change did not touch them. Nothing in this version re-binds a lapsed check (`confirm` is not built), so that cost is visible but not yet payable.
- **Normalizer.** `vsect-norm/0`, named on every event, is a documented approximation of `core.md` §3.1 (no CommonMark parse; fenced code and display math kept byte for byte; paragraphs reflowed; any math change is a change). It also strips md-press's own markers (`<!--md-press:KIND:…-->`, one line, at the end of a site; the grammar is md-press's, agreed 2026-10-30), which record a formatting decision and not anything the statement says. That rule was added after every version in the asf store was computed and before md-press wrote any marker, so on every text ever hashed the function is unchanged; it ships under the same name for that reason. `vsect-norm/1` is reserved for the design's CommonMark normalizer. **Object-format defect:** the normalizer's name is written into each canonical object and so is part of every version hash, which makes renaming the normalizer a store-wide rehash; the next object format should carry the name on events only. Until then, a normalizer change that alters existing values is a migration, not a rename.
- **Event ids** are the SHA-256 of the event's canonical JSON, including its time; so `take` is made idempotent by lookup (the review item already taken on that target), not by hash. The design's §5.4 duplicate detection and §7.6 idempotency cannot both hold by hash alone; this is a design finding.
- **Built-in kind `review`**, not `report`: the harness treats "report" in a path an agent writes as a cue to report in chat instead of writing the file (the lead coordinator, 2026-10-30).
- **No marks are written into records** (`core.md` §10) in this version. `refute` records the event and the cascade; `check` reports every refuted or broken statement whose file carries no mark, so the gap stays visible.
- **`revise` asks reworded/redefined only when a recorded check rests on the old version**; otherwise it records `change: unclassified` with that reason. The design asks every time; asking 246 times with nothing at stake would be asking what does not matter.
- **Deleted records** that were never minted but were checked or refuted at a past revision (`- at: <git rev>`) still get a fate: `revise` walks them too.
- **Planned targets.** A store may declare where it says which not-yet-written records are planned (`planned: {find: ["0*/OUTLINE.md"], cell: missing}`: table rows in those files carrying that cell name a planned record by `#slug`). An edge naming a planned record is reported as planned, not dangling — the rule `bin/lint-outline` applies, so the two tools agree.
- **Not built:** `next` ranking, cascade marks, `verify` and `brief` writing, `orient`, outlines, free-form review intake, `contest`, `decide`/`purpose` records, cross-store addressing, interrupted-write recovery, the unassigned-prose heuristic (moot at record grain).
