## 1. `\(1\)` → `$1$` inside a link destination — silent URL corruption

**Severity: highest of these.** It changes a URL to point at a file that does not exist, in a way no reader would notice and the gate cannot catch.

```
- ...6819c33cc21ef33f81157d27_AISI%20Research%20Agenda%20Publication%20\(1\).pdf)
+ ...6819c33cc21ef33f81157d27_AISI%20Research%20Agenda%20Publication%20$1$.pdf)
```

**Cause, from STATUS.md's own description** of `normalize_paren_math` (2026-08-06): the deterministic `\(…\)` → `$…$` pass applies "when the interior indicates math (LaTeX command, math glyph/Greek, `_`/`^`, **or a short space-free identifier** — `\(see above\)` stays prose)." `1` is a short space-free identifier, so the interior test says math. Joseph's first read was "`\(` is automatically assumed to be math"; the more precise version is that the indicator list's last clause admits any short token, and a scraped URL with markdown-escaped literal parens hits it.

**Why parser-siting didn't prevent it.** The site is the whole paragraph line, and the link destination lives *inside* that paragraph — so "markdown structure is structurally out of reach" holds at block level but not at inline level. Code spans are already excluded by the detector; link destinations and autolinks are not.

**Why the gate is silent.** Exactly as STATUS.md says of the two stages: the math pass deliberately changes rendering, so render-equality cannot apply to it. That is correct and is also why an inline-level masking step has to carry this on its own — there is no net underneath.

**Possible direction:** mask inline non-prose spans (link destinations, autolinks, raw HTML attributes) inside a prose site before promotion, the way code spans already are. Alternatively, require a stronger indicator than "short space-free identifier" when the `\(…\)` sits inside a link destination — though masking seems the more general fix, since the same exposure exists for anything else living inside inline markup.

**Reproducer:** `~/src/AISI-responses/aisi-research-agenda.md` line 564, restored by hand in commit `400f2ab`; a `--math` run there reproduces it. That repo now carries a KNOWN HAZARD note in its `.md-pressignore` naming the line to re-check after any future `--math` run, which should be deletable once this is fixed.

## 2. `·` (U+00B7) used as a prose separator, promoted to `$\cdot$`

43 occurrences on 6 lines in 2 files. The promotions were all of this shape:

```
- **Control cluster:** AI control · control measures · control protocols · control evaluations
+ **Control cluster:** AI control $\cdot$ control measures $\cdot$ control protocols $\cdot$ control evaluations

- | Work/blog listing | https://www.aisi.gov.uk/work · https://www.aisi.gov.uk/blog | [V] |
+ | Work/blog listing | https://www.aisi.gov.uk/work $\cdot$ https://www.aisi.gov.uk/blog | [V] |
```

Also hit a `·`-separated list of backticked filenames.

**The mapping is correct; the use is not.** `·` → `\cdot` is right for multiplication, and the *same run* promoted it correctly inside real math — `$\alpha_{\text{time}} = \nu \cdot \eta^\ast \cdot c_{\min}$` is exactly right. So this is a separator-vs-operator confusion, not a table error. The math-content consistency gate passes by construction, since `\cdot` does map back to a `·` present in the original.

**Worth knowing that this will recur estate-wide:** ` · ` is house separator style. The global `CLAUDE.md` uses it in its own status legend (`**FULL** … · **PARTIAL** … · **UNREAD**`) and in the register-translation list, and the memory index uses it throughout. A `--math` run over those would produce the same thing.

**Possible direction:** treat a space-flanked `·` whose neighbours are word tokens, links, or code spans as prose. Or, at line level: if the only math evidence on a line is `·` separators, the line isn't a math line. The multiplication use in practice appears adjacent to symbols already inside a math span, which may make the two cases cleanly separable.

**Reproducer:** `~/src/AISI-responses/asf-notes/32-aisi-research-brief.md` lines 107–111, 137, 139 and `asf-notes/AUDIT-register-pass-2026-08-12.md` line 120 (reverted in commit `312e95b`).

## 3. Render-equality gate refuses a two-line construct — "please report"

The message asked, so: `aisi.md` (a Greenhouse job-board scrape) was `SKIPPED — result would change rendered document (bug or unsupported construct; please report)`. Bisected to a minimal two-line reproducer:

```
- Discounts and benefits for cycling to work, donations and retail/gyms.··\n
·····\n
```

A list item whose text ends in a hard break (two trailing spaces), followed by a **whitespace-only but not empty** line (five spaces). The transformation the engine wants, byte-level via stdin:

```
in:   ...retail/gyms.  \n     \n        (5-space line)
out:  ...retail/gyms.  \n\n             (whitespace-only line emptied)
```

**I did not determine which side is wrong** — whether emptying a whitespace-only line is unsafe in this position (a normalization bug) or the HTML fingerprint is over-sensitive to it (a gate bug). You have the fingerprint in hand and it should be a one-minute question from the reproducer; I'd have been guessing. Either way the gate did its job: the file was left byte-identical, which is why the scrape survived the run intact.

**Reproducer:** `~/src/AISI-responses/aisi.md`, or the two lines above alone in a file.

## 4. `--math` and the wrap pass are not idempotent together

`asf-notes/31-asf-orientation-notes.md` reported dirty on `md-press --check` immediately after md-press had written it, wanting two further line joins. **Joseph's diagnosis, which supersedes my guess:** the parser knows what is already inside math segments and what is not, so promoting Unicode math to LaTeX changes the input the break classifier reads — "so yeah, not strictly idempotent."

Filed as a note rather than a defect, with two observations that may or may not matter to you: `invariants_hold_on_all_fixtures` asserts idempotence, and presumably runs without `--math`, so the property is true where it is tested; and `--help`'s "re-running is idempotent" is now conditional on `--math` being off, which a reader would not guess.

## Two things the run confirmed rather than broke

**The ambiguous-break reporting is genuinely usable.** Every uncertain break came with its probability and the exact manual reversal ("re-separate and append two trailing spaces"). That is how the nav/TOC damage in item 1's file got noticed and repaired at all — Joseph spotted the joins because the tool had said which ones it was unsure about. Worth protecting if that output is ever considered for trimming.

**`.md-pressignore` is the right instrument for scraped external pages, and it worked once applied.** The first run joined 19 nav/TOC line breaks in a scrape of AISI's published site at p=0.40–0.47 (reported, each one). All of that is now moot for that file — Joseph elected to have it canonicalized and its purposeful breaks carry two trailing spaces — but the general lesson matched your EXCLUSIONS note exactly: reformatting a provenanced copy is render-equivalent and still wrong, and only a human knows which files those are. That repo now excludes two scrapes and deliberately does not exclude the third, with the reason recorded at the entry.
