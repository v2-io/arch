# FEEDBACK: MDX documents are read as CommonMark, 2026-10-31

*From the Opus instance that built limen's MX-1 (`~/src/limen/impl/mx1-mdx-and-fence-languages.md`, merged as limen 9a85e6e). limen now reads MDX component rows as MDX does, and Joseph asked that md-press hear about it too: "Please go ahead and file a note / feature request to md-press." md-press still reads these files as CommonMark, and on them its `--fix` would edit code. I have not read `src/` beyond a grep, so the directions below are guesses from outside. The measurements are from md-press 0.3.0, run report-only (nothing written) with `--no-log --no-math`.*

## 1. What happens

Documentation sites built on MDX (Mintlify, Docusaurus) write components as tags on rows of their own, with markdown inside, and save the pages as `.md`:

```text
<CodeGroup exclude="shell">
  ```python Python
  client = anthropic.Anthropic()
  ...
  ```
</CodeGroup>
```

CommonMark reads a row that is only `<CodeGroup …>` as an HTML block (type 7) running to the next blank line, so the fence opener under it is inside that block. The rest of the sample then reads as paragraphs and headings, and from there the fence pairing inverts: each closer opens a fence and each opener closes one. MDX reads the row as a component, and the fence as a fence. GitHub renders such a page with CommonMark, which is why the breakage is easy to miss.

md-press reads the page the CommonMark way, so it judges the python sample as prose. On `~/src/_ref/claude-docs/docs/en/build-with-claude/compaction-thinking-blocks.md` (on a copy), the report is "8 line breaks joined, 47 breaks kept and marked", all inside the python sample: `model=MODEL,` ⏎ `max_tokens=8192,` kept and marked with two trailing spaces, `history.append({…` joined over three rows, and so on.

In code a join can do more than move whitespace. In `_core/ennaos/docs/claude-docs/en/api/agent-sdk/custom-tools.md`, a `<CodeGroup>` swallows a TypeScript fence, and md-press would join rows 114–128 (code `0b1ka`). Row 114 is `prompt: generateMessages(),  // Use async generator for streaming input`, so the join turns every line after it into part of that comment.

## 2. Why the render gate does not catch it

It is the `.udon` mechanism again. Under CommonMark, joining two rows of a paragraph does not change the render, and neither does marking a break that CommonMark collapses anyway, so the render-equality gate passes. But CommonMark is not this author's renderer. The README's sentence about UDON fits exactly: a mangled line "renders as unremarkable markdown text — which is why the guard sits in front of the gate instead of relying on it."

## 3. How far it reaches

limen's MDX reading changes the structure of 1,144 of the 33,469 `*.md` files under `~/src`. All of them are scraped MDX documentation:
- the two claude-docs copies (`_ref/claude-docs`, `_core/ennaos/docs/claude-docs`);
- `_ref/voyageai-docs`;
- `agent-core/harness-velocity/data/raw/{anthropic,devin,qoder}`.

No authored estate file reads differently. Over those 1,144, md-press reports that 745 would change. I classified each break it would change by where its two lines fall in limen's MDX reading:

| md-press decision | inside a code block (MDX reading) | touching a component-tag row | elsewhere |
|---|---|---|---|
| join | 3,048 | 664 | 5,895 |
| keep + mark | 5,502 | 195 | 4,961 |

"Elsewhere" is not mostly prose. In a random sample of 16 of its joins, 14 were inside MDX's JavaScript: `export const Foo = () => { … }` component bodies, with style objects and arrays, which CommonMark reads as paragraphs. The other two joined a genuine two-line blockquote. So most of what md-press proposes on these files is code or component structure, and its share of ordinary prose is small. The classifier and the decision dump are reproducible (§6). The per-category numbers come from limen's structure, so they are only as good as limen's MDX reading, and limen does not yet read MDX's `export`/`import` blocks either.

Who would run md-press here? These are reference and scraped trees, not anyone's prose. The exposure is a caller who presses a whole tree. md-press has no recursive mode, so that means `find … | xargs md-press --fix`. `agent-core/harness-velocity/data/raw` is research data, and a silent edit to code samples would corrupt what it records.

## 4. What I think md-press should do

**A guard in front of the gate, like `.udon`'s, is what I'd do first.** md-press's safety argument is render equality under CommonMark, and for an MDX document it cannot vouch for MDX's render. So the honest default is to decline, with the reason reported, and an explicit override (`--allow-mdx`, parallel to `--allow-udon`, and like it not implied by `--force`). Two signals, both cheap. I'd check each against the corpus before trusting it:
- **A row that is only PascalCase JSX tags, outside fences and frontmatter:** `<Note>`, `</CodeGroup>`, `<Card title="…" />`. The name's first letter is upper and some letter is lower, so `<div>` and `<DIV>` keep CommonMark's reading. Attributes follow JSX syntax: `name`, `name="…"`, `name={…}`, `{...spread}`. Allow at most two valueless names, because angle-bracketed prose such as `<Runtime versions if they matter:>` (a template in `agent-core`) or `<Implements the identical patch to …>` (a transcript in `ai-risk-model`) otherwise looks like a tag. limen's first pass made exactly that mistake on those two files. limen's implementation of this test, with its unit cases, is `tags_on` in `~/src/limen/structure/src/markdown/mdx.rs`.
- **MDX's module syntax at column 0, outside fences:** `export const|function|default …` or `import X from '…'`. A bare `import`/`export` at the start of a line is too loose, since hard-wrapped prose can start a line with "export the…"; the binding forms are not prose. This one is a guess. I did not measure it.

A `.mdx` extension is the third, trivially. Whether md-press already declines or accepts `.mdx` when named I didn't check.

**Pressing MDX properly is a larger thing, and I would not start it now.** The estate has no authored MDX. It has only reference copies, whose wrapping is someone else's. If it ever matters, there are two halves:
- **Component rows.** limen's provider handles them by parsing a view in which a component row is an HTML comment (so it ends on its own row and may interrupt a paragraph, as MDX's flow tag does) and a component's interior is dedented by its extra indentation (MDX disables indented code). The resulting columns are then mapped back. `View::of` / `unshift` in `mdx.rs` is self-contained, and it is the kind of thing the "shared crate" idea in `~/src/limen/design/structure-engine.md` (§md-press kinship) was about.
- **The ESM blocks.** These are JavaScript, and nothing in the comrak path sees them. Handling them would mean recognising them and treating them as verbatim.

A render-equality oracle for MDX would need both halves, which is why the guard comes first.

**A stopgap, not md-press's to make:** a `.md-pressignore` at the scraped roots would close the exposure today. Those directories belong to their projects, so that call is Joseph's or theirs.

## 5. A smaller observation from the same run

Inside the component regions md-press also decides at tag rows: 664 joins and 195 marks touch a row like `</Check>` or `<Tip>`. An example is administration-api.md L12, an unsure join (p 0.47) of "…min API keys through the Claude Console." with `</Check>`. Under MDX, joining a closing tag onto the previous line probably still parses (as inline JSX), so this is more about the tool's judgment showing than about damage. A guard would make it moot.
