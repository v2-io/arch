## Executive Summary

This document specifies requirements for an AI conversation system designed for **long-term, persistent interactions** where conversation integrity and recoverability are paramount. The system must handle:

- **Conversations lasting weeks or months** with hundreds of turns
- **Network failures and API errors** without data loss or corruption
- **Complex multi-step tool executions** with rollback capabilities
- **Rich context tracking** including time passage, workspace state, and resource usage
- **Multiple failure modes** with guided recovery workflows

**Key Design Principles:**
1. **Never corrupt conversation state** - fail gracefully, block dangerous actions
2. **Always recoverable** - every failure has a defined recovery path
3. **Transparent operations** - user understands system state at all times
4. **Context-aware** - system tracks time, resources, and workspace changes
5. **Audit-first** - complete record of all API interactions

## Core Message Handling

### REQ-1: Message Source Attribution

**Requirement:** The system MUST explicitly distinguish between different message sources.

**Message Types:**
- **User-typed messages** - Explicitly tagged as coming from the human user
- **Automatic system messages** - Generated by the system (idle notifications, status updates)
- **Mid-processing messages** - Sent by user while AI is processing
- **Urgent messages** - High-priority messages sent during processing

**Rationale:** AI needs clear context about message origin to respond appropriately. A system-generated "Joseph has been away from keyboard" notification should be treated differently than Joseph saying "I've been away from keyboard."

**User Experience:**
- User's messages clearly wrapped in identifiable tags
- Automatic messages use distinct formatting
- AI can reference message source in responses

---

### REQ-2: Idle Detection and Notification

**Requirement:** The system MUST detect user inactivity and notify the AI after a configurable threshold (default: 60 seconds).

**Behavior:**
- Timer starts when AI finishes responding (not when user starts composing)
- Timer resets on user activity (typing, not just sending)
- Single notification per idle period (no repeated notifications)
- Natural language time format ("2 minutes and 30 seconds", not "02:30")

**Keystroke-Level Detection:**
The system SHOULD detect the FIRST KEYSTROKE before Enter is pressed, to distinguish between:
- User genuinely idle (timer fires)
- User composing message (timer suppressed)

**Rationale:** Long pauses have meaning in conversations. The AI should know when the user stepped away (contextual pause) vs. when they're thinking (intentional pause).

**Example Notification:**
```
<automatic-response>Joseph has been away from the keyboard for 3 minutes and 45 seconds.</automatic-response>
```

---

### REQ-3: Mid-Processing Message Queue

**Requirement:** The system MUST allow users to send messages WHILE the AI is processing, queueing them for automatic submission when processing completes.

**Features:**
- Accept multi-line input during processing
- Queue multiple messages if needed
- Auto-submit queued messages when AI finishes
- Clear queue when control returns to user
- Visual confirmation when message queued

**Priority Levels:**
- **Normal priority** - Regular incoming messages
- **Urgent priority** (optional) - High-priority interruptions with distinct formatting

**Rationale:** Users shouldn't need to wait for AI to finish before providing additional context or corrections. This enables more natural, flowing conversations.

**User Experience:**
```
[AI is working...]
User types: "Actually, use the other config file"
[Message queued]
[AI finishes]
[Queued message auto-submitted]
[AI responds with correction]
```

---

### REQ-4: Auto-Save on Every Turn

**Requirement:** The system MUST automatically save conversation state after EVERY message exchange, without requiring user action.

**Save Points:**
- After user message sent
- After AI response received
- After tool execution completed
- Before any risky operation

**Format:**
- Structured, append-only format (e.g., JSONL)
- Timestamped entries
- Preserves message structure (text, images, tool calls, etc.)

**Rationale:** Conversations are valuable. Losing work due to crashes, network issues, or user error is unacceptable. Auto-save makes conversations resilient by default.

**Guarantees:**
- No conversation progress lost to crashes
- Can resume from exact state at any time
- No "Did I save?" anxiety for users

## Context Awareness & Tracking

### REQ-5: Comprehensive Context Snapshots

**Requirement:** The system SHOULD provide detailed context about the conversation environment with each message.

**Context Components:**

#### Resource Usage
- **Token count** - Current context window utilization (percentage of maximum)
- **Token breakdown** - System prompt, tools, conversation history
- **Cache statistics** - Tokens read from cache, savings from caching
- **Warnings** - Alert when approaching context limits (e.g., 80%, 95%)

#### Time Awareness
- **Time elapsed** - Duration since last message
- **Current timestamp** - Full date/time with timezone
- **Previous timestamp** - When last message was sent
- **Date boundaries** - Flag when crossing day boundaries

#### Workspace State
- **Current working directory** - Where user is operating
- **Version control status** - Git branch, modified files, recent commits
- **Workspace changes** - Files added/modified/deleted since last message

**Delivery:**
Context snapshot sent as structured data with each user message, formatted for AI consumption.

**Rationale:** AI should understand:
- "It's been 3 hours since you asked that" (temporal context)
- "You're 85% through your context window" (resource awareness)
- "You switched branches since last message" (workspace context)

---

### REQ-6: Context Snapshot Compression

**Requirement:** The system MUST compress older context snapshots to reduce token consumption in long conversations.

**Strategy:**
- Keep most recent N snapshots (e.g., 3) in full detail
- Compress older snapshots to essential information only (time delta, date change)
- Preserve all other message content unchanged

**Compression Example:**
```
FULL SNAPSHOT (Recent):
- Context Usage: 45.2% (452,300/1,000,000 tokens), 547,700 remaining
- Time Passage: 15 minutes, 30 seconds
- Current: 2025-10-10 14:32:15 PDT (Afternoon)
- Previous: 2025-10-10 14:16:45 PDT (Afternoon)
- Working Directory: /Users/joseph/src/project
- Git Status: branch main, 3 modified files, 2 untracked
- Recent commits: [list of 3]

COMPRESSED SNAPSHOT (Older):
- Time Passage: 15 minutes, 30 seconds
- Date: 2025-10-10 → 2025-10-10 (Same Day)
```

**Savings:**
- Full snapshot: ~500-800 tokens
- Compressed snapshot: ~50-100 tokens
- In 50-turn conversation: Save ~35,000 tokens (3.5% of 1M context)

### REQ-7: Visual Time Delta Format

**Requirement:** The system SHOULD represent time passage in a human-readable yet structured format.

**Requirements:**
- Natural language: "2 hours, 15 minutes, 30 seconds"
- Machine-parseable structure for consistency
- Cultural/project-appropriate symbolism (if desired)
- Clear date boundary indicators

**Example Formats:**
```
Natural: "2 hours, 15 minutes, and 30 seconds"
Structured: "↺02:15⊙" (project-specific notation)
Date change: "📅 NEW DAY: 2025-10-09 → 2025-10-10"
Same day: "⌚ SAME DAY"
```

### REQ-8: Token Counting with Official API

**Requirement:** The system MUST use the AI provider's official token counting API (not estimates) for accurate context management.

**Why Official API:**
- Exact token counts (no approximation error)
- Accounts for: system prompt structure, tool definitions, message formatting, caching
- Same tokenizer as actual inference
- Prevents unexpected "context too large" errors

**What to Count:**
- System prompt tokens
- Tool definition tokens
- All message tokens (user and assistant)
- Context snapshot tokens
- Image tokens (if applicable)

**Display:**
- Current context window percentage
- Tokens remaining
- Warning colors (green < 80%, yellow 80-95%, red > 95%)
- Cache hit statistics

## Conversation Persistence & Recovery

### REQ-9: Complete Audit Trail

**Requirement:** The system MUST maintain a complete, immutable audit trail of all API interactions.

**Audit Components:**

#### Request Logging
- Full API request body (system prompt, messages, tools, parameters)
- Headers and API version
- Timestamp (preparation start time)
- Request size in bytes

#### Response Logging
- Full API response body
- Response size in bytes
- Response timestamp
- HTTP status code

#### Telemetry Tracking
- **Timing breakdown:**
  - Preparation duration (request building)
  - Connection time (TCP handshake)
  - Request send time (upload)
  - Response receive time (download)
  - Total duration
- **Size metrics:**
  - Request size
  - Response size
- **Audit trail management:**
  - Git commit for each request
  - Git commit for each response
  - Commit messages include timing info

**Storage:**
- Structured format (JSON)
- Version controlled (git)
- Separate directory per conversation
- Sequential numbering (turn-001, turn-002, etc.)

**Rationale:**
- **Debugging** - Exactly what was sent/received at any point
- **Provenance** - Immutable record with git timestamps
- **Analysis** - Performance metrics, token usage patterns
- **Recovery** - Reconstruct conversation state from audit trail

### REQ-10: Conversation Continuation

**Requirement:** The system MUST support resuming conversations from saved files, maintaining full state.

**Resume Behavior:**
- Load complete message history
- Restore message structure (text, images, tool calls, tool results)
- Recalculate token usage for current context
- Detect incomplete states (see Error Handling section)
- Continue numbering (turns, audit trail)

**What's Restored:**
- All messages (user, assistant, tool results)
- Thinking blocks (if preserved)
- Context snapshots (if enabled)
- Tool execution history

**What's Re-Initialized:**
- Token tracking (recalculated from loaded messages)
- Audit directory (new session, references old session)
- Turn counter (continues from message count)

**Use Cases:**
- Resume after closing application
- Resume after crash or forced quit
- Resume after days or weeks
- Resume on different machine (if files transferred)

### REQ-11: Initial Context Loading

**Requirement:** The system SHOULD support injecting temporary context on the first message only.

**Behavior:**
- Context loaded from file/string
- Included in first API request
- NOT saved to conversation history
- NOT included in subsequent requests

**Use Cases:**
- Session-specific instructions
- Temporary briefing documents
- One-time context setting
- Dynamic system prompt augmentation

**Example:**
```
Initial Context: "This session is about debugging the auth module. See attached error logs."
[Context sent only with first message]
[NOT saved to conversation file]
[Subsequent messages proceed normally]
```

### REQ-12: System Prompt Composition

**Requirement:** The system SHOULD support modular composition of system prompts through imports.

**Import Syntax:**
```
@import ./module-a.md
@import ../shared/module-b.md
@import /absolute/path/module-c.md
```

**Features:**
- Recursive imports (imported files can import other files)
- Circular import detection (prevent infinite loops)
- Multiple path resolution strategies:
  - Relative to current file
  - Relative to project root
  - Absolute paths
  - Home-relative paths
- Inline error messages (import not found, circular import detected)

**Rationale:**
- **Modularity** - Separate identity, capabilities, philosophical foundations
- **Reusability** - Share common sections across multiple AIs
- **Maintainability** - Update one file, affects all importers
- **Version control** - Track changes to each component independently

## API Provider Features

### REQ-13: Prompt Caching

**Requirement:** The system MUST use the provider's prompt caching feature to reduce costs and latency.

**Caching Strategy:**

The system SHOULD establish multiple cache points to maximize cache hit rate:

1. **System Prompt** - Largest, most stable (changes rarely)
2. **Tool Definitions** - Medium size, very stable
3. **Conversation History** - Large, somewhat stable (grows over time)

**Cache Placement:**
- Place cache breakpoint AFTER stable content
- Place cache breakpoint BEFORE changing content
- For conversation history: cache all-but-most-recent messages

**Expected Savings:**
- Turn 1: No cache (creates cache, full cost)
- Turn 2: ~60% cost reduction (system + tools cached)
- Turn 3+: ~90% cost reduction (system + tools + history cached)
- Latency: ~85% reduction on cache hits

**Cache Lifecycle:**
- Cache duration: Per provider specification (typically 5 minutes)
- Cache invalidation: Automatic when content changes
- Cache warming: Happens naturally through usage

### REQ-14: Extended Thinking (Reasoning)

**Requirement:** The system SHOULD use extended thinking/reasoning features when available.

**Configuration:**
- **Thinking budget** - Token allocation for reasoning (e.g., 25,000 tokens)
- **Output budget** - Token allocation for response (e.g., 8,000 tokens)
- **Total budget** - Combined limit (e.g., 33,000 tokens)

**Behavior:**
- AI can use thinking budget to reason before responding
- Thinking content may be hidden from user (provider-dependent)
- Thinking summary may be shown (character count, redaction notices)
- Thinking blocks preserved in conversation history (for provider)

**Thinking Disable Conditions:**
Extended thinking SHOULD be automatically disabled when:
- Temperature ≠ 1.0 (provider limitation)
- Top-p < 0.95 (provider limitation)
- User explicitly disables

**User Notification:**
System MUST warn user when sampling parameters disable thinking.

**Requirement:** The system MUST support large context windows (e.g., 1M tokens) through provider beta features.

**Requirements:**
- Enable beta flags for large context
- Track usage as percentage of maximum
- Warn at configurable thresholds (default: 80%, 95%)
- Accurate token counting for large contexts

**User Experience:**

### REQ-16: Interleaved Thinking Mode

**Requirement:** The system SHOULD support interleaved thinking when available (thinking blocks interspersed with text).

**Behavior:**
- AI can think, respond, think more, respond more
- Enables "progressive disclosure" response pattern
- More natural for complex, multi-part answers

**Example Flow:**
```
[Thinking: Analyzing the question...]
Here's the first part of my answer...
[Thinking: Considering edge cases...]
And here's an important caveat...
[Thinking: Formulating final recommendation...]
So in conclusion...
```

### REQ-17: Server-Side Web Search

**Requirement:** The system SHOULD support server-side web search tools when available.

**Features:**
- AI can invoke web search during response
- Search results returned server-side (not through client)
- Citations preserved in conversation history
- Multi-turn search support (AI can reference previous search results)

**Critical Implementation Requirement:**
The system MUST preserve ALL server-side tool result blocks in conversation history, including:
- Search result content (often encrypted)
- Citation blocks
- Encrypted indices
- Any provider-specific metadata

**Rationale:** Provider may need these blocks to resolve citations in subsequent turns. Deleting them breaks multi-turn search conversations.

## Error Handling & Failure Recovery

### REQ-18: Incomplete Conversation State Detection

**Requirement:** The system MUST detect incomplete conversation states on startup or after failures.

**Incomplete States:**

#### State A: Tool Use Pending
- **Detection:** Last message is from AI, contains tool use requests, no following user message
- **Cause:** Tools were requested but never executed (crash, ctrl-c, etc.)
- **Symptom:** Conversation ends mid-workflow
- **Recovery:** Execute pending tools OR rollback to retry user message

#### State B: User Message Orphaned
- **Detection:** Last message is from user (plain text), no assistant response
- **Cause:** API timeout, connection loss, crash after sending
- **Symptom:** User's message has no response
- **Recovery:** Resend user message

#### State C: Tool Results Orphaned
- **Detection:** Last message is from user (tool results), no assistant response
- **Cause:** Tools executed, but no final AI response
- **Symptom:** Tool execution completed but conversation incomplete
- **Recovery:** Send tool results to get AI response

**User Experience:**
```
⚠️  INCOMPLETE CONVERSATION - RUN /resume FIRST

The assistant requested tool execution that was never completed.

You MUST choose one:
→ Run /resume to execute the pending tools
→ Run /rollback to remove tool request and retry your message

(All other messages are blocked until resolved)
```

---

### REQ-19: Blocking State Machine

**Requirement:** The system MUST block new user messages when conversation is in incomplete state.

**Behavior:**
1. Detect incomplete state on startup or after failure
2. Set blocking flag with failure type
3. Display clear guidance for recovery
4. REJECT all new user input (except recovery commands)
5. Clear blocking flag only after successful recovery

**Rationale:**
Prevents "talking past" an error and corrupting conversation history. Forces explicit recovery decision.

**Example Interaction:**
```
> User tries to send new message

⚠️  Cannot send new messages - incomplete state detected!

Your last message has no response.
Type /resume to resend it, or /rollback if available.

> [Input blocked, re-prompt]
```

---

### REQ-20: API Server Error Handling

**Requirement:** The system MUST handle server errors (500, 502, 503) with exponential backoff retry.

**Retry Strategy:**
- **Maximum retries:** 10 attempts
- **Backoff timing:** 10s, 20s, 40s, 80s, 160s, 300s (capped at 5 minutes)
- **Total patience:** ~23 minutes across all retries

**Retry Loop:**
1. API returns server error (500/502/503)
2. Extract error message from response
3. Display retry count and wait time
4. Wait with visual countdown (for waits > 30s)
5. Retry request
6. If exhausted: Set failure state, suggest manual recovery

**User Experience:**
```
⚠️  Server error (503). Retry 3/10 in 40s...
Error: Service temporarily unavailable

[After exhausting retries]
❌ Server error persists after 10 retries.
(Total wait time: ~23 minutes)
Type /resume to manually retry when the API recovers.
```

---

### REQ-21: Timeout Handling with Progressive Increase

**Requirement:** The system MUST handle timeouts with progressively longer timeout values.

**Progressive Strategy:**
- **Attempt 1:** 4 minutes (normal responses)
- **Attempt 2:** 5 minutes (deep thinking responses)
- **Attempt 3:** 10 minutes (maximum patience for complex requests)
- **Total patience:** 19 minutes across 3 attempts

**Rationale:**
- Most responses complete in < 4 minutes
- Extended thinking can take 5-8 minutes
- Complex multi-tool chains might need 10 minutes
- Avoids premature timeout on legitimate long-running requests

**User Experience:**
```
[Attempt 1 timeout at 4 minutes]
⏱️  API call timed out after 4 minutes. Retrying with 5-minute timeout...
(The assistant may be thinking deeply about your request)

[Attempt 2 timeout at 5 minutes]
⏱️  API call timed out after 5 minutes. Final retry with 10-minute timeout...
(Complex responses can take time - giving maximum patience)

[Attempt 3 timeout at 10 minutes]
❌ API call timed out after 10 minutes (all retries exhausted).
(Total wait time: 19 minutes. The request may be too complex.)
Type /resume to retry, or continue with a new message.
```

---

### REQ-22: Connection Error Handling

**Requirement:** The system MUST handle connection errors (refused, DNS failures) with immediate failure.

**Behavior:**
- No automatic retry (unlike server errors and timeouts)
- Immediate failure notification
- Set failure state for manual recovery
- Suggest checking network/VPN/firewall

**Rationale:**
Connection errors usually indicate local network issues that won't resolve automatically.

---

### REQ-23: Resume Command

**Requirement:** The system MUST provide a resume command to recover from failures.

**Resume Behavior by Failure Type:**

#### Resume from Tool Results Orphaned
1. Remove tool results temporarily (to rebuild tracking snapshot)
2. Add back tool results
3. Make API call to get AI response
4. Update conversation with response

#### Resume from User Message Orphaned
1. Rebuild tracking snapshot with current context
2. Resend user message (with updated snapshot)
3. Wait for AI response
4. Update conversation

#### Resume from Tool Use Pending
1. Extract all tool use blocks from last AI message
2. Execute each tool
3. Truncate large tool results (> 500KB) to prevent API timeout
4. Add tool results as user message
5. Make API call to get AI response

**Common Behavior:**
- Show "Resuming conversation..." message
- Clear failure state on success
- Re-set failure state if resume fails
- Update tracking snapshots after successful resume

---

### REQ-24: Rollback Command

**Requirement:** The system MUST provide a rollback command to undo failed tool requests.

**Rollback Behavior:**
1. Verify failure state is "tool use pending"
2. Remove last AI message (the one with tool use)
3. Display original user message that will be resent
4. Set failure state to "user message orphaned"
5. User runs /resume to retry

**Use Case:**
```
1. User: "Read the config file"
2. AI: [Requests tool: read-file with wrong path]
3. User realizes path is wrong
4. User: /rollback
   [AI's tool request removed]
   [Shows: "Your message that will be resent: Read the config file"]
5. User: /resume
6. AI: [Hopefully gets it right this time]
```

---

### REQ-25: Conversation Repair

**Requirement:** The system MUST provide a repair command to fix conversation integrity issues.

**Repair Operations:**

#### Orphaned Tool Use Detection
- **Issue:** AI message has tool use, but no following user message with tool results
- **Fix:** Insert placeholder tool results (error message explaining they were missing)

#### Partial Tool Results
- **Issue:** AI requested 3 tools, but only 2 results returned
- **Fix:** Add missing tool results (error placeholders)

#### Tool Use Followed by Text
- **Issue:** User sent text message after AI requested tools (should be tool results)
- **Fix:** Convert message to array with tool results first, then text

#### Backup Before Repair
- **Requirement:** MUST create backup of original file before making any changes
- **Location:** Same directory, `.backup` suffix
- **Restoration:** User can manually restore if repair causes issues

**User Experience:**
```
CONVERSATION REPAIR

Scanning for integrity issues...

Issues found:
  • Message 23: Assistant tool_use without following user message
  • Message 47: Tool uses abc123, def456 lack results

Repairs made:
  ✓ Added placeholder tool results after message 23
  ✓ Added missing tool result for abc123
  ✓ Added missing tool result for def456

Original backed up to: conversation_backup.jsonl
Repaired conversation saved

You can now try sending your message again.
```

### REQ-26: Conversation Diagnostics

**Requirement:** The system MUST provide a diagnostics command to inspect conversation state.

**Diagnostic Checks:**

#### Message Statistics
- Total message count
- User vs. assistant message counts
- Messages with tool results
- Large messages (> 100KB)

#### Size Analysis
- Total conversation size
- System prompt size
- Per-message size breakdown

#### Integrity Checks
- **JSON serialization** - Can all messages serialize properly?
- **Character encoding** - All UTF-8? Any null bytes?
- **Message alternation** - Proper user → assistant → user pattern?
- **Tool completeness** - All tool uses have results?

#### State Detection
- **Incomplete states** - Orphaned tools, messages, results?
- **Thinking blocks** - How many? Any redacted?
- **Last message analysis** - What type? Any issues?

**Output:**
```
CONVERSATION DIAGNOSTICS

Messages: 47 total (24 user, 23 assistant)
  Message 12: Contains 2 tool result(s)
  Message 38 (user): 245KB [LARGE]

Total conversation size: 1,234.5KB
System prompt size: 45.2KB

⚠️  Encoding Issues:
  Message 38: Contains null bytes

⚠️  Last assistant message contains 1 tool_use block(s)
    → Conversation may be incomplete (run /resume or /repair)
```

## Tools & Capabilities

### REQ-27: File Operations Tools

**Requirement:** The system MUST provide basic file I/O tools.

#### Read File
- **Input:** File path (supports ~, relative paths, absolute paths)
- **Output:** Complete file contents as string
- **Errors:** File not found, permission denied

#### Write File
- **Input:** File path, content string
- **Output:** Success confirmation
- **Behavior:** Creates parent directories if needed, overwrites existing files
- **Errors:** Permission denied, disk full

#### Execute Command
- **Input:** Shell command string
- **Output:** stdout, stderr, exit status (all three separately)
- **Behavior:** Full shell access, no timeout
- **Errors:** Command not found, execution errors (in stderr)

---

### REQ-28: Text Editor Suite

**Requirement:** The system SHOULD provide a multi-command text editor tool with safety features.

#### View Command
- **Input:** File path, optional line range
- **Output:** File contents with line numbers, or directory listing
- **Format:** `  123 | line content`

#### String Replace Command
- **Input:** File path, old string, new string
- **Output:** Success (1 replacement) or error
- **Safety:** MUST reject if pattern matches > 1 location
- **Error Details:** Show line numbers of ALL matches if multi-match detected
- **Behavior:** Uses single-replacement (not global) even if safety check fails

**Multi-Match Protection Example:**
```
Input: Replace "def process" with "def process_v2"

[String appears on lines 45, 123, 456]

ERROR: Pattern matches 3 locations in file. Please make your pattern more specific to match only one location.
Matches found at:
  - Line 45
  - Line 123
  - Line 456
```

#### Create Command
- **Input:** File path, file contents
- **Output:** Success or error
- **Behavior:** Creates parent directories, fails if file exists (no overwrites)

#### Insert Command
- **Input:** File path, line number, text to insert
- **Output:** Success or error
- **Behavior:** Insert after line N (line 0 = beginning, line EOF = append)

### REQ-29: Token Counting Tools

**Requirement:** The system SHOULD provide tools for AI to check token usage.

#### Count File Tokens
- **Input:** File path
- **Output:** Exact token count using official API
- **Use Case:** AI checks if file will fit in context before reading

#### Count Context Tokens
- **Input:** Optional flags (summary mode, reset counters)
- **Output:** Current context usage, percentage, breakdown, cache stats
- **Modes:**
  - Summary: One-line percentage display
  - Detail: Full breakdown by component
- **Use Case:** AI monitors context usage proactively

### REQ-30: Sampling Control Tool

**Requirement:** The system SHOULD allow AI to adjust its own sampling parameters.

#### Set Sampling Command
- **Input:** Temperature (0-1) OR top-p (0-1)
- **Mutual Exclusivity:** Can only set one at a time, not both
- **Output:** Success, current settings, thinking status

**Thinking Interaction:**
- Temperature ≠ 1.0 → Disables thinking
- Top-p < 0.95 → Disables thinking
- MUST warn user when thinking disabled

**Use Cases:**
- AI increases randomness for creative tasks (temperature = 1.0)
- AI decreases randomness for precise tasks (temperature = 0.3)
- AI uses top-p for different sampling strategy
- AI resets to defaults when needed

**Requirement:** The system SHOULD allow AI to enable/disable tracking snapshots.

**Behavior:**
- **Input:** Boolean (enable or disable)
- **Effect:** Future messages include/exclude tracking snapshots
- **Output:** Confirmation of new state

**Use Cases:**
- AI finds snapshots too verbose → disables
- AI needs context info → enables
- AI toggles for specific workflow phases

## User Interface & Experience

### REQ-33: Multi-Line Input

**Requirement:** The system MUST support natural multi-line message composition.

**Behavior:**
- User types first line, presses Enter → continues accepting input
- User types more lines, presses Enter → continues accepting input
- User presses End-of-Input signal (e.g., Ctrl+D) → sends message
- Empty messages ignored (re-prompt)
- Slash commands single-line only

**User Experience:**
```
> This is a multi-line
message that spans
several lines.
^D

[Message sent with newlines preserved]
```

## Safety & Validation

### REQ-37: Context Window Warnings

**Requirement:** The system MUST warn users when approaching context limits.

**Warning Levels:**
- **80-95%** - Yellow caution notice
- **>95%** - Red critical warning with recommendation

**Messages:**
```
[At 82%]
⚠️  Note: Context window is 82.3% full.

[At 96%]
⚠️  WARNING: Context window nearly full! Consider starting a new conversation.
```

### REQ-38: Large Data Protection

**Requirement:** The system MUST protect against API timeouts from oversized requests.

#### Tool Result Truncation
- **Trigger:** Tool result > 500KB
- **Action:** Truncate to 400KB with explanatory note
- **Note:** `[TRUNCATED: File too large for API. Original size: N bytes]`

#### Request Size Monitoring
- **Warning at 1MB:** Show request size
- **Critical at 10MB:** Warn that API timeout likely

---

### REQ-39: Image Size Validation

**Requirement:** The system MUST validate image sizes before embedding.

**Validation:**
- Maximum size: 5MB (per provider limit)
- If oversized: Show warning, keep original reference syntax (don't embed)
- If missing: Show warning, keep original reference syntax

**User Feedback:**
```
[Warning: Image too large (8.5MB > 5MB): screenshot.png]
[Embedded image: diagram.png (347KB)]
```

## Appendix: Failure Mode Matrix

| Failure Mode | Detection | Auto-Retry | Manual Recovery | Data Loss Risk |
|--------------|-----------|------------|-----------------|----------------|
| **Server Error (500-503)** | HTTP status | ✅ 10x exponential | /resume after exhaustion | None (saved before send) |
| **Timeout (4-10min)** | Exception | ✅ 3x progressive | /resume after 19min | None (saved before send) |
| **Connection Error** | Exception | ❌ Immediate fail | /resume | None (saved before send) |
| **Tool Use Orphaned** | State check on load | ❌ | /resume or /rollback | ⚠️ Moderate (tools not executed) |
| **User Message Orphaned** | State check on load | ❌ | /resume | ⚠️ Moderate (response missing) |
| **Tool Results Orphaned** | State check on load | ❌ | /resume | ⚠️ Low (can re-request) |
| **Tool Execution Error** | Try/catch in tool | ❌ Returns error to AI | AI handles | None (error passed to AI) |
| **Large Tool Result** | Size check | ✅ Auto-truncate at 500KB | N/A | ⚠️ Partial (truncated) |
| **JSON Serialization** | /debug scan | ❌ | Manual message editing | 🔴 High (corrupted file) |
| **Encoding Issues** | /debug scan | ❌ | Manual message editing | ⚠️ Moderate (garbled text) |
| **Orphaned Tool Blocks** | /repair scan | ❌ | /repair auto-fix | ⚠️ Low (placeholder results added) |
